# AGENTS.md

## Cursor Cloud specific instructions

This repo is a **secrets-gated, multi-platform content publishing toolkit** (Excalibur Social / Posts EMDR),
not a long-running web app. There is no server, no test suite, and no lint config. The runnable surface is
a set of **stdlib-only Python 3 CLI scripts** in `scripts/`, orchestrated by Cursor agent rules in
`.cursor/rules/posts-emdr-orchestrator.mdc`. Standard commands and the full pipeline are documented in
`README.md` and `posts-emdr-memory/CLOUD-SETUP.md` — reference those rather than duplicating.

### Dependencies / environment

- **No dependency install is needed.** All scripts use the Python 3 standard library only — there is no
  `requirements.txt`/`pyproject.toml`, no `package.json`, and no virtualenv. The startup update script only
  runs `python3 scripts/materialize_cloud_env.py`, which writes `posts-emdr-memory/*.env.local` from any
  Cursor Cloud Secrets that are set (idempotent; a no-op when no secrets are present).

### Diagnostics that always run without secrets

- `python3 scripts/incident_queue.py --project-root .` — pre-run Fixic gate (exit `2` = open incidents).
- `python3 scripts/cloud_preflight.py` — readiness report. Exits `2` (`NOT READY`) until publishing secrets
  are configured; this is expected, not a setup failure. The script itself running is the health signal.
- Max/Telegram `--dry-run` parse real topic markdown and make **no network calls**, but still require the
  relevant `*_BOT_TOKEN` env var to be non-empty (any value passes the dry-run check), e.g.
  `python3 scripts/send-max-draft.py --topic <id> --dry-run`.

### Non-obvious gotchas

- **Nothing publishes without Cursor Cloud Secrets.** Required for phase-1 scripts: `MAX_BOT_TOKEN`,
  `MAX_CHAT_ID`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_CHAT_IDS`, `TELEGRAM_CHANNEL_UTM_SOURCES`,
  `ZERNIO_API_KEY`, `ZERNIO_FACEBOOK_ACCOUNT_ID`, `RUNWARE_API_KEY`, `FTP_SERVER`, `FTP_USERNAME`,
  `FTP_PASSWORD`, `FTP_SERVER_DIR` (see `posts-emdr-memory/cloud-secrets-checklist.txt`).
- **`scripts/send-vk-post.py` cover prep uses macOS-only `sips`** and will fail on a Linux cloud pod.
  In cloud, VK is not published via that script's API path — VK is phase 2 via **MCP `mcp-kv`
  `vk_create_post_with_photo`**, driven by `output/{topic}/vk-mcp-handoff.json` (generated by
  `publish-topic.py`). `VK_ACCESS_TOKEN` is intentionally **not** used in cloud.
- **`cover.png` is gitignored** and Runware cover generation needs `RUNWARE_API_KEY` + network, so a full
  `publish-topic.py` run (even `--dry-run`, because the VK step reads `cover.png`) requires generating a
  cover first on a fresh checkout.
- **b17 + TenChat (phase 3) need a local Undetectable Browser** on the operator's Mac (`127.0.0.1:25325`);
  they are skipped in cloud, and `publish-topic.py` writes `output/{topic}/browser-local-handoff.md` instead.
